## Findings

### F1. Fetch tracking history can incorrectly veto a push to a different push URL
- Category: bug
- Severity: medium
- Confidence: CLEAR BUG
- Location: pkg/commands/git_commands/branch_sync_push.go:81, :172; pkg/gui/controllers/branch_sync_push_flow.go:68
- Problem: Both the disabled-menu check and PrepareBranchPush unconditionally infer destination divergence from the remote's fetch mapping. A configured pushurl can point to a different repository. Its branch need not have the history fetched from remote.url. The resulting claim that a plain push would be rejected is false, and the backend refuses the push before Git can decide.
- Scenario / evidence: Native probe `/tmp/probe-branch-sync-I5E3ud` created separate fetch.git and push.git destinations. Both started at B; fetch.git/topic advanced independently to F; local topic advanced from B to L; push.git/topic stayed at B. After fetching origin, `merge-base --is-ancestor refs/remotes/origin/topic refs/heads/topic` returned 1. This is exactly the predicate that disables/refuses the fork's ordinary push. Nevertheless, the same ordinary command generated by BranchPushCommand, `git -c push.autoSetupRemote=false push --porcelain --no-follow-tags --recurse-submodules=no -- origin refs/heads/topic:refs/heads/topic`, succeeded and advanced push.git/topic to L. Explicit force leases remain safe against unexpected server state, but an automatically chosen lease from the fetch repository also need not describe the push repository.
- Suggested fix: Do not turn fetch-tracking divergence into a hard plain-push veto when the push destination is not established as the fetched destination. Keep Git's native fast-forward rejection authoritative in that case, without adding an implicit network fetch. Add a regression with distinct fetch and push URLs; review automatic lease-source labeling for the same topology.

### F2. Invalid/unsupported default pull policy hides the explicit methods needed to recover
- Category: bug
- Severity: medium
- Confidence: CLEAR BUG
- Location: pkg/gui/controllers/branch_sync_current_pull_flow.go:77, :87, :100; pkg/commands/git_commands/branch_sync_pull_review.go:360, :367
- Problem: chooseIntegration presents alternatives only for three recognized default failures. Unsupported configured rebase modes and invalid pull.ff values return ordinary errors instead, so presentIntegrationChoices is never reached. The unsupported-mode error specifically says to choose a method explicitly, but the UI gives no way to do that.
- Scenario / evidence: Configure `pull.rebase=bogus`, then complete the reviewed fetch for the checked-out branch. PrepareCurrentPullIntegration(Default) reaches resolvePullReviewMethod and returns `unsupported configured pull rebase mode ...; choose a method explicitly`. isUnavailableCurrentPullDefault returns false, and chooseIntegration returns the error rather than opening the method menu. An explicit integration request bypasses that configuration parser and could run. The same menu blockage occurs for an invalid pull.ff. This was traced end-to-end in code; no new test was written or run for this case.
- Suggested fix: Distinguish unavailable/default-policy errors from repository/inspection failures and show the former as a disabled configured-method row while preserving explicit alternatives. Test unsupported rebase mode and malformed pull.ff through the controller after fetch.

### F3. Terminal handoff repeats full integration inspection on the UI thread
- Category: code-quality
- Severity: medium
- Confidence: n/a
- Location: pkg/gui/controllers/branch_sync_integration_exec.go:108, :113; pkg/commands/git_commands/branch_sync_pull_review.go:276; pkg/commands/git_commands/rebase_ignored_files.go:25, :147
- Problem: The worker performs CurrentPullIntegrationCommand, then the queued UI callback calls it again synchronously. This is a full plan preparation, not a small source/HEAD check: native ref/config/worktree queries, ancestry queries, clean status for rebases, target ls-tree, a replay-history log, ignored-file enumeration, and collision-content hashing can all run before RunSubprocess releases the UI terminal.
- Scenario / evidence: A large repository or a large ignored build artifact colliding with an incoming tracked path can require reading substantial history and hashing the entire artifact on the UI thread, even immediately after the same worker inspection. fingerprintRegularFile uses io.Copy to hash all bytes. This is a deterministic blocking call path; no latency benchmark was run. Network fetch/push and credential prompts in the active scoped flows themselves are dispatched to workers, which is good.
- Suggested fix: Keep expensive plan/risk reconstruction on a worker with input held through terminal handoff; reserve a narrowly bounded final source/repository check for the UI callback. Preserve re-review on changed inputs and Git's normal concurrency model. Add a controller assertion about which phase executes the expensive inspection.

### F4. The global-fetch guarantee does not match native configured fetch behavior
- Category: docs
- Severity: medium
- Confidence: n/a
- Location: docs-master/fork/Guide.md:451; pkg/gui/controllers/fork_fetch.go:11, :29; pkg/commands/git_commands/sync.go:61, :70; pkg/gui/controllers/remotes_controller.go:85
- Problem: The guide says f fetches every remote from any pane and never moves branches. In Remotes, the local remote.fetch binding wins and fetches the selected remote. Global fetch also obeys git.fetchAll (false omits --all) and arbitrary configured fetch refspecs; it has none of the scoped-fetch protection against writes into refs/heads.
- Scenario / evidence: In the probe above, after checking out main, set `remote.origin.fetch=+refs/heads/topic:refs/heads/topic`. Running the default global-fetch command `git fetch --all --no-write-fetch-head` forcibly changed the off-branch topic from L to F. Git printed `(forced update)`. Thus even an off-branch history rewrite is possible under the unconditional documented guarantee. The Remotes exception is explicit in fork_fetch.go's comment and the keymap, but absent from this guide sentence.
- Suggested fix: Resolve the contract question below before changing behavior; at minimum document the existing Remotes/configuration exceptions accurately. Do not silently implement a new refspec policy during this review.

### F5. Dormant parallel implementations add substantial maintenance surface
- Category: code-quality
- Severity: low
- Confidence: n/a
- Location: pkg/gui/controllers/branch_sync_stack_push_flow.go:14; pkg/commands/git_commands/branch_sync_current_pull.go:39; pkg/commands/git_commands/branch_sync_local.go:61
- Problem: Repository-wide call-site searches find branchStackPushFlow construction only in its tests. PrepareCurrentBranchPull / CurrentBranchPullCommand likewise have only test callers plus their internal revalidation call. The active UI uses fetch-first CurrentPullReview / CurrentPullIntegrationPlan instead. The native-pull implementation retains an additional local-remote rewrite inspector that only that dormant path needs.
- Scenario / evidence: The dormant stack-push file adds 195 source lines and 758 test lines. The superseded current-pull file adds 133 source lines and 407 test lines, plus its exclusive helper and additional literal-config test coverage. branch_sync_push_flow.go explicitly says wider-stack push is deferred. These tests may verify their own implementations well while providing no coverage of a reachable feature. This is separate from intentionally retained upstream legacy methods in sync_controller.go, which have external callers.
- Suggested fix: Confirm that retaining these prototypes is intentional. If deferred behavior has no supported production entry point, remove the dormant fork implementations and exclusive tests in a scoped cleanup, retaining history in Git. Keep active fetch-first policy/signature helpers used elsewhere.
